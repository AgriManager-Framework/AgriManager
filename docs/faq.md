# FAQ and limitations

## Using the code

**Do I need a GPU?**
No, for building datasets, running scripted policies, training and evaluating
the neural baselines, and the [quickstart](getting-started/quickstart.md).
Yes, for training or scoring language-model policies.

**The first run downloads a lot of data.**
The 20-crop WOFOST pool (used by T1.2 and the default WOFOST smoke tests) is a
17.6 GB archive and takes about 65 GB once extracted into `.cache/wofost_gym/`.
The maize pool used by the quickstart and by Tier 2 is 0.25 GB. Make `.cache` a
symbolic link to a large disk if needed.

**A dataset built on one machine fails on another.**
Built parquet files store absolute paths (weather cache, crop traits). Rebuild
the dataset on the new machine, or rewrite the paths as
`experiments/rebuttal_confirmatory_eval/normalize_eval_suite_paths.py` does for
the test suites.

**Why is there no `--crop` or `--dataset` flag on the run scripts?**
Each `run_*.sh` under `experiments/` is one fixed experiment; variants get their
own script. This keeps every paper number tied to one file. See
[CONTRIBUTING](contributing.md).

**What do the internal names in file names mean?**
Files and directories starting with `e4_` belong to the held-out test suite;
`e5_` is the script that scores a checkpoint on it; `rebuttal_confirmatory_eval/`
is the directory that builds it. Method labels such as `Ag heuristic (paper)` in
the CSV tables mean the scripted agronomic reference.

**My scores differ slightly from the paper's.**
Greedy decoding is deterministic on one machine, but vLLM results are not
bitwise identical across GPU types or drivers: a few episodes per 128-scenario
split can change. Also check that you scored the terminal revision, in the
response format the checkpoint was trained with, on the whole split.

## Interpreting results

**Is the scripted agronomic reference an expert or an upper bound?**
No. It is a conservative codified schedule, uncalibrated against experts or
optimal control. On WOFOST even the untrained think model scores above it on
every Tier 2 target. A normalized score of 5 means five times the gap between
no-action and that schedule.

**Why is the weather-regime setting (T1.1) not normalized?**
On its test splits the scripted reference is at or below no-action (gap from
−0.148 to +0.017 profit-equivalent t/ha, negative on 8 of 10 targets), so the
gap cannot serve as a denominator. T1.1 is reported as gain over no-action.

**Why can the neural baseline not run on Tier 2 and Tier 3?**
The fixed-interface PPO has the observation size and the action set built into
its network, so it cannot run when they change, and it needs retraining when
the objective changes. The statement is about that baseline only. The
action-menu setting includes a schema-capable neural baseline (MaskablePPO over
a shared action vocabulary) and a target-trained PPO; see
[Baselines](benchmark/baselines.md#neural-baselines).

**Which results are confirmatory?**
Results on the held-out test suite with three training seeds per arm.
Validation-only and single-seed results are exploratory: training curves, the
T1.2 per-crop breakdown, single-seed PPO `n8` on T1.1, and the backbone
comparisons.

## Known limitations

- **Simulation only.** All scores are simulator outputs from WOFOST, DSSAT and
  Cycles. Simulator fidelity bounds every conclusion; nothing here is field
  advice.
- **Cycles crop-growth test suites are small.** A scenario there is fixed by
  its weather year at one site; each of the three suites holds 13 physical
  scenarios (2004 to 2016). Seed-level SDs are valid; scenario-level standard
  errors overstate precision. The first build of these suites reused the eight
  validation years and was replaced.
- **Cycles yield saturates.** On the Cycles yield tuple of T3.2 every
  competent policy reaches the same yield on every scenario, so that tuple
  does not separate policies.
- **DSSAT reference.** The submitted paper's DSSAT reference values were set by
  hand; the final numbers use a code reconstruction of the schedule. See
  [Baselines](benchmark/baselines.md#three-disclosures).
- **T1.1 groups.** The test-suite weather groups use a new explicit rule; the
  `id` group is the residual after the four tails and is milder than a random
  draw, which favours the in-distribution end of ID-to-OOD comparisons.
- **Per-run records.** Part of the scenario-level scoring bundles of September
  2026 was lost; aggregate tables survive and bundles are being regenerated by
  re-scoring the same checkpoints ([Reproducing](guides/reproduce.md)).
- **One backbone for the confirmatory results.** Confirmatory results use
  Qwen3-4B-Instruct. Other backbones are single-seed and exploratory, and on
  Llama-3.2 the reasoning advantage reverses on most WOFOST tuples.
- **Settings outside the paper.** The code also contains a schema-corruption
  analysis (T2.4) and a rice variety experiment (APP1). Neither is part of the
  paper's eight settings or its test suite.
